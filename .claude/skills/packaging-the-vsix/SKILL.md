# Packaging the VSIX

Lumina Code is tested from an installed VSIX, not from the Extension
Development Host. Every change to core, the GUI or the extension needs a
repackage before it can be tested.

## When to Use

Use this skill when asked to package, build, rebuild, reinstall or ship the
extension, or when a change must be tested in the real editor.

## Full Sequence

All paths are relative to `continue-upstream/`. Run the steps in order; skip
step 1 only if nothing under `gui/src` changed.

```
Packaging:
- [ ] 1. Build the GUI          (only if gui/src changed)
- [ ] 2. Prepackage
- [ ] 3. Package
- [ ] 4. Install
- [ ] 5. Tell the user to reload
```

### 1. Build the GUI

```
cd gui
npm run build
```

Takes several minutes. The VSIX ships `extensions/vscode/gui`, refreshed from
`gui/dist` by the next step — so a skipped GUI build silently ships the old
interface.

### 2. Prepackage

```
cd extensions/vscode
$env:SKIP_INSTALLS='true'
node scripts/prepackage.js --target win32-x64
```

`SKIP_INSTALLS=true` avoids a full `npm install` of roughly fifteen minutes.
It also skips generating two schemas; see "Generated files" below if either is
missing.

This wipes `out/` and `bin/` first, then copies the GUI, onnxruntime,
tree-sitter, sqlite, ffmpeg and LanceDB. It ends with `All paths exist`. Anything
else is a failure — read it, do not retry blindly.

### 3. Package

```
npx @vscode/vsce package --out ./build --no-dependencies --target win32-x64
```

This triggers `vscode:prepublish`, which rebuilds `out/extension.js` with
esbuild. Expect roughly 98 MB and 410 files.

### 4. Install

```
code --install-extension .\build\lumina-code-win32-x64-<version>.vsix --force
```

Take `<version>` from `extensions/vscode/package.json`. Bump it when iterating,
so it is possible to tell which build is installed.

### 5. Reload

The install does not take effect until the window reloads. Tell the user to run
**Developer: Reload Window**. You cannot do this for them.

## Generated Files

These are in `.gitignore` and absent on a clean checkout. Each one fails the
build if missing:

| Missing file | How to produce it |
|---|---|
| `core/vendor/tree-sitter.wasm` | `cd core && npm run prepare:tree-sitter-vendor` |
| `extensions/vscode/config-yaml-schema.json` | `cd packages/config-yaml && npm run generate-schema`, then copy `schema/config-yaml-schema.json` into `extensions/vscode/` |
| `extensions/vscode/continue_rc_schema.json` | Generated by prepackage without `SKIP_INSTALLS` |
| `models/all-MiniLM-L6-v2/onnx/model_quantized.onnx` | Download from `https://huggingface.co/Xenova/all-MiniLM-L6-v2/resolve/main/onnx/model_quantized.onnx` (~22 MB) |

## Verifying the Install

Do not trust "successfully installed". Confirm the built GUI is the installed
one by comparing hashes:

- `gui/dist/assets/index.js`
- `extensions/vscode/gui/assets/index.js`
- `~/.vscode/extensions/luminacode.lumina-code-<version>/out/extension.js`

The first two must be identical. A mismatch means the GUI build did not reach
the package.

## What Breaks When Installed

An installed VSIX no longer lives inside the repository, so anything derived
from the extension's own location breaks. Two were fixed and are worth knowing:

- The root `.env` is found via `LUMINA_ROOT`, exported at activation from the
  open workspace folder (`src/extension/luminaRoot.ts`).
- The `Lumina_PC` runtime root also resolves from the workspace folder.
- The shipped skill library is `extensions/vscode/skills`, packaged into the
  VSIX and pointed at by `LUMINA_BUNDLED_SKILLS_DIR`, exported at activation
  from `context.extensionUri`. A skill placed anywhere else only loads on the
  machine where this repository happens to be the open workspace.

Both need `c:/Lumina Code` open as the workspace. If provider keys come back
empty in an installed build, check the **Lumina Code: Activation** output
channel — it prints the resolved Lumina root.
